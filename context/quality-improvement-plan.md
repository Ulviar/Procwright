# План завершения технического упрощения

## Цель и границы

Рабочий план следующего этапа для разработчиков и независимых аудиторов. Цель пользователя — довести до 10/10
дизайн публичного API, архитектурные границы, поддерживаемость реализации, работу с отказами и ресурсами,
систему тестирования и документацию для разработчика. Переносимость, доказанность производительности и
устойчивость сопровождения командой не входят в этот этап.

Оценка не заменяет доказательства: по каждой из шести шкал должны быть проверены все относящиеся к ней сценарии
текущего MVP, закрыты подтверждённые разрывы и выполнен независимый аудит. Зелёный gate сам по себе не доказывает
простоту архитектуры или удобство API. Этот временный план удаляется после переноса результатов в contracts,
ADR, tests и scorecard.

## Проверяемые результаты

| Область | Критерий завершения | Доказательства |
| --- | --- | --- |
| API | Последовательные scenario/Draft semantics, ранняя валидация, понятные cancellation/close/outcome contracts без противоречий между Java, Kotlin и integrations | Public API и negative tests, внешние consumers, аудит реальных сценариев |
| Архитектура | Общий process runtime; для каждого инварианта один владелец; зависимости и optional layers соответствуют границам модулей | Ownership review, boundary gates, актуальная proof map |
| Поддерживаемость реализации | Разобраны все области backlog 3; удалены необоснованные состояния, протоколы и защитные подсистемы ADR-0025 | Сопоставление переходов и владельцев до/после, проверка типовых изменений, независимый code audit |
| Отказы и ресурсы | Deadline, cancellation, output ownership, limits и cleanup имеют ясные границы; нет известных утечек, deadlocks или неоднозначного terminal outcome в поддерживаемых сценариях | Негативные и конкурентные behavioral tests, реальные процессы, bounded stress |
| Тестирование | Критические инварианты связаны с поведенческими proofs; тесты различают успех и ошибочный обход обязательного действия | Ревизия доказательств, управляемые fixtures, regression/stress, CI на итоговом commit |
| Документация | Читатель может выбрать сценарий, запустить пример и понять failure/resource contract без противоречий или обещаний сверх реализации | Scenario walkthrough, canonical compiled examples, strict docs, независимый аудит |

## Последовательность

- [x] Независимая исходная ревизия API, runtime, tests и документации; подтвердить конкретные разрывы кодом.
- [x] Pool startup/replenishment и callback cancellation: typed startup outcome, один monitor replenishment и одна
  identity-registration отмены; defects и лишняя координация устранены.
- [ ] Pool retirement: проверить полезность промежуточных futures и отдельного dispatch bookkeeping.
- [x] Session terminal state и output ownership: один outcome, объяснимые границы settlement и один pair close после
  process outcome и logical mode settlement.
- [ ] Process-tree cleanup и provider boundary: завершить бюджет гарантий ADR-0025, сохранив полезную очистку.
- [ ] Согласовать deadlines, отмену, limits, failure reasons и выбор session/pool в API, tests и документации.
- [ ] Проверить весь MVP по шести критериям; исправить все существенные замечания, выполнить итоговые gates и аудит.

Изменение гарантии выполняется одновременно с владельцем поведения, тестом и документацией. Конкретные findings
живут в текущем рабочем diff и сообщениях аудита; отдельный архив отчётов не создаётся. Публикация нового artifact,
выбор remote registry и новые возможности вне MVP не требуются для этого этапа.

Следующие структурные проверки — retirement и process-provider/tree boundary. Кандидаты на удаление не считаются
defects без подтверждения и не оправдывают ослабление поддерживаемых lifecycle guarantees.
