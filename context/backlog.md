# Активный бэклог

## Назначение и статус

Бэклог задаёт согласованный с пользователем порядок актуализации Procwright и критерии завершения работ.
Приоритет — Java 25, актуальный tooling и простота реализации; поддержка старых JVM ради потенциальной аудитории
не является целью.

Ниже описано целевое состояние. Текущие код, ADR и release policy продолжают описывать действующие гарантии до
соответствующего изменения реализации. Запись в бэклог не означает выполнения миграции.
Завершённые пункты удаляются после переноса устойчивых решений в ADR, contracts, tests и scorecard.

## 2. Перейти на Java 25 и полностью актуализировать код и tooling

Статус: следующий этап после объединения основной разработки.

Цель: Java 25 — единственные minimum runtime, compilation target и базовая JDK разработки/CI. Сохранение совместимости
с Java 17/21 не требуется. Переход включает весь репозиторий и полноценный пересмотр реализации.

- [ ] Оформить заменяющее [ADR-0020](decisions/ADR-0020-java-release-variants.md) решение о едином baseline Java 25.
  Согласованно обновить toolchains, Java/Kotlin targets, publication metadata и проверки минимальной JVM.
- [ ] Удалить варианты сборки 17/21, ветвления по версии JVM, reflection-доступ к стандартным API новой JDK и
  compatibility fallbacks, которые больше не нужны. Упростить CI до проверки Java 25 на Linux, macOS и Windows.
- [ ] Провести ревизию всего production-кода, Kotlin extensions, integrations, fixtures, tests и examples на применение
  актуальных стабильных возможностей Java/Kotlin. Использовать современные API коллекций, языка и стандартной
  библиотеки там, где они упрощают код; удалить заменённые самописные helpers и дублирование.
- [ ] Пересмотреть threading и execution lifecycle: прямые virtual-thread API, владение executor/task, отмену,
  deadlines и cleanup. Сохранить осмысленные ограничения количества процессов, задач и накопленных данных;
  virtual threads сами по себе не задают эти ограничения.
- [ ] Актуализировать весь tooling до последних стабильных совместимых версий на момент выполнения: JDK 25 patch,
  Gradle wrapper/plugins, Kotlin/coroutines, JUnit, Jackson, JSpecify, форматтеры, Javadoc/Dokka,
  Python/uv/MkDocs и GitHub Actions. Проверить также инструменты вне охвата Dependabot, убрать неиспользуемые.
  Версии фиксировать воспроизводимо вместе с checksums, action SHA и dependency verification.
- [ ] Проверить совместимость связки инструментов и миграционные изменения. Preview/incubator API и prerelease
  tooling оценивать отдельно с явным обоснованием пользы; максимальная актуальность по умолчанию означает stable.
- [ ] Обновить README, public docs, `context/release/`, test tiers, инструкции аудиторам, examples и quality checks
  вместе с реализацией. Удалить устаревшие обещания совместимости и команды проверки Java 17/21.

Готово, когда весь код и tooling прошли ревизию, все модули и публикуемые артефакты требуют Java 25,
остатки поддержки 17/21 удалены, а regression/stress, formatting, Java/Kotlin API documentation, public docs,
external consumers и publication-readiness проходят на одном commit. CI проверяет Java 25 на трёх ОС;
изолированные normal/POM-only consumers подтверждают реальные metadata артефактов. Применимые обновления Dependabot
не остаются отложенными. Использование каждой новой языковой возможности само по себе не является критерием готовности.

## 3. Продолжить упрощение runtime и прояснение контрактов

Статус: продолжение текущей работы после Java 25; локальные упрощения, необходимые для миграции, входят в пункт 2.

Цель: поведение сценария можно понять по небольшому числу владельцев состояния, а пользовательские гарантии
выражены однозначно и подтверждены наблюдаемыми проверками.

- [ ] Продолжить [ADR-0025](decisions/ADR-0025-runtime-guarantee-budget.md): пересмотреть дорогие защитные механизмы
  относительно реалистичных отказов и требований пользователя. Для каждой снятой гарантии одновременно изменить
  владельца поведения, tests и документацию.
- [ ] Разобрать сложные места pool startup/retirement/replenishment, session terminal state, output ownership,
  process-tree cleanup и callback cancellation. Удалять дублирующиеся состояния, промежуточных посредников,
  неиспользуемые abstractions и неочевидные протоколы между helpers.
- [ ] Для каждого сценария явно определить начало и границы deadline, правила отмены до/после передачи запроса,
  владение stdout/stderr, момент логического завершения и пределы физической очистки.
- [ ] Зафиксировать пределы памяти, очередей, количества процессов и callbacks, область их действия и поведение при
  исчерпании лимита. Уточнить stable failure reasons, диагностические возможности и best-effort границы.
- [ ] Согласовать критерии выбора session и pool во всех точках входа документации: одна сессия переиспользует один
  процесс; пул предназначен для конкурентных независимых запросов к взаимозаменяемым workers.
- [ ] Сохранять поведенческие доказательства happy/failure/edge paths; заменять проверки внутренней формы кода
  проверками пользовательского результата там, где структура сама не защищает необходимую границу.
  Актуализировать [scenario contracts](scenario-contracts.md), [владельцев инвариантов](invariant-architecture.md)
  и [proof map](quality/invariant-proof-map.md) в тех же изменениях.

Готово, когда для каждого затронутого инварианта есть один владелец и релевантная проверка, контракты согласованы с
кодом и examples, а обязательные аудиты не содержат незакрытых P0–P2. Оценивать число независимых состояний,
синхронизационных границ и связей компонентов; уменьшение длины отдельных файлов недостаточно.

## Выполнение

Работать проверяемыми шагами: группы dependency/tooling updates, базовая миграция Java,
рефакторинг отдельных областей runtime. Широкий охват ревизии не требует одного большого изменения.
Проверки и независимые аудиты выбирать по [протоколу шага](audits/step-audit-protocol.md).
На каждом этапе сохранять scenario-first API, единый runtime и полезные пользовательские гарантии.
